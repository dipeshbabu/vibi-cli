# How vibi encrypts

This is the design behind "the server stores ciphertext it cannot read". Every primitive named here is the one in `packages/shared/src/`; the file names are given so the description can be checked against the code.

## Keys

Each user has one X25519 key pair (`crypto.ts`), generated by the client on the first machine they enroll. Keys are raw 32-byte values encoded as unpadded base64url, the JWK encoding for OKP keys. A key's **fingerprint** is the first 16 base64url characters of the SHA-256 of the public key; it identifies keys in envelopes and is shown in the dashboard and the CLI.

The public key is stored on the server in the clear. The private key is stored on the server only **wrapped** with the user's encryption password (`userkey.ts`):

```
kek        = scrypt(NFKC(password), salt[16], N=2^16, r=8, p=1) -> 32 bytes
ciphertext = AES-256-GCM(kek, nonce[12], privateKey, aad = "vibi/v1/userkey:" + fingerprint)
```

The scrypt parameters travel with the blob so they can be raised later. The password is never sent anywhere; a machine that enrolls later downloads the wrapped key and unlocks it locally. Passwords are at least 12 characters. There is no recovery: a forgotten password means the key, and everything encrypted for it, is lost.

The unlocked private key is kept on a machine only if the user asks (`~/.vibi/keys/user.json`, mode 0600); otherwise it stays in memory for one command.

## Envelopes

A session is uploaded as one **version** with an envelope (`envelope.ts`; schema in `sessions.ts`). The content and its metadata (title, working directory, model, message count, source path, start time) are encrypted with a fresh random content key; the content key is wrapped once per recipient:

```
contentKey      = random 32 bytes, one per version
ciphertext      = AES-256-GCM(contentKey, nonce, trace bytes,  aad = "vibi/v1/content")
meta.ciphertext = AES-256-GCM(contentKey, nonce, JSON metadata, aad = "vibi/v1/meta")
for each recipient public key R:
  (epk, esk) = ephemeral X25519 pair
  kek        = HKDF-SHA256(ECDH(esk, R), salt = epk || R, info = "vibi/v1/wrap")
  wrapped    = AES-256-GCM(kek, nonce, contentKey, aad = "vibi/v1/wrap:" + fingerprint(R))
```

The envelope header carries the content nonce, the ciphertext length and its SHA-256, the encrypted metadata, and one `{fingerprint, epk, nonce, wrapped}` entry per recipient. The server validates the header's shape and checks that the uploaded object has the declared length; it never has a key that opens any part of it. A recipient decrypts by finding the entry with their fingerprint, recovering the content key with their private key, and verifying the ciphertext hash before decrypting.

Sending a stored version to another user wraps the same content key for their public key (`addRecipient`); the ciphertext is not re-uploaded.

## Sending to someone without a key

If the recipient has no key yet (no account, or an account that never enrolled), the sender's client makes a key pair for them (`passphrase.ts`): the private key is wrapped as above but with a random 12-character passphrase (31-symbol alphabet, about 59 bits) and scrypt at N=2^17, and the pair is registered as a **provisional recipient**. The session is encrypted for that key like any other. The passphrase is shown to the sender to pass on out of band. When the recipient enrolls, the client asks for it, unwraps the provisional private key locally, re-wraps the content keys for the recipient's own key and asks the server to swap the recipient entries. The server holds the wrapped provisional key and the ciphertext, which is why the passphrase is machine-generated and the derivation deliberately slow.

## What the server can see

Plaintext on the server: account email, public keys and fingerprints, machine names, which sessions exist and when they changed, the harness kind (Claude Code, Codex and so on), sizes, the optional plain-text label a user gives a session, who sent what to whom, and envelope headers. Not on the server in any readable form: session content, titles, working directories, model names, passwords, private keys, passphrases.

## Trust assumptions

- The client code is honest. That is why it is public; build it yourself if you do not want to trust the published executables (see SECURITY.md).
- Recipients' public keys come from the server. A sender sees the fingerprint of the key they encrypt for, and recipients see fingerprints in the dashboard; comparing them out of band is the defence against a substituted key.
- Node's `node:crypto` (and Bun's implementation of it in the standalone build) provides X25519, HKDF, scrypt and AES-GCM correctly; the test suite round-trips every primitive between the two runtimes.
